description: Reset an existing apitest project directory back to a clean slate and point it at a different target API — destructive, only run with explicit target directory and new spec confirmed by the human operator.

# Project bootstrapper

**Destructive.** This wipes prior scenarios/customSteps/queries/run artifacts in the target
project directory. Never run this prompt proactively or infer a target/spec on your own — it must
be given, or you must ask for, both: the **target project directory** (a real apitest project —
has its own `apitest.config.ts`; default to `examples/assertquest` only if the human confirms
that's what they mean) and the **new spec** (a URL or local file path). If either is missing or
ambiguous, stop and ask.

Never operate outside the target directory. Every command below runs with that directory as cwd —
never delete or write files at repo root or in a different example.

## Step 1 — confirm this is a real apitest project

- Read `<target>/apitest.config.ts` and check `<target>/package.json` exists — if either is
  missing, stop; this isn't an apitest project directory.
- Note the current `spec:` value so your final report can say what it changed *from* and *to*.

## Step 2 — clean, but only the regenerable/project-specific pieces

Delete, inside `<target>/` only:
- `scenarios/**` (all `*.scenario.yaml` / `*.cases.yaml`)
- `customSteps/**` (all `*.ts` — stale ones left behind would silently collide by export name with
  anything added later, so they must go)
- `queries/**` (API-specific SQL query library)
- `seeds/**` if present
- `.spec-cache/` (regenerated by `apitest sync`)
- `allure-results/`, `allure-report/`, `test-results/`, `playwright-report/`
- `schemas/scenario.schema.json` (regenerated by `apitest schema`)

**Never delete:** `node_modules/`, `package.json`, `package-lock.json`, `playwright.config.ts`,
`README.md`, `environments/*.env` (real credentials — only `.env.example` is safe to regenerate;
if a live `dev.env` exists, leave it and flag in your report that it still holds credentials for
the *old* API). `apitest.config.ts` is not deleted either — Step 3 overwrites it.

Before deleting anything, list exactly what you're about to remove (paths, not full contents).
Scope every delete command to the specific subpaths above — never a bare recursive delete of the
whole target directory or an unscoped wildcard.

## Step 3 — point at the new spec

```
cd <target>
npx apitest init --spec <new-spec>
```

This overwrites `apitest.config.ts` and `environments/dev.env.example`. Read the command's console
output — it names every `securitySchemes` entry it couldn't fully auto-configure (oauth2/
openIdConnect gets a stubbed `bearer-login` role with a guessed or `TODO` login path; query-string
api-key isn't auto-configurable at all and needs a hand-written `kind: "custom"` `AuthStrategy`,
see `src/types/config.ts`). Read the resulting `apitest.config.ts` and confirm it's at least
syntactically sensible — hand-fix obviously-wrong guesses but leave genuinely ambiguous choices for
the human to review, and say so in your report.

## Step 4 — mandatory config the human still has to fill in

You cannot invent real credentials. Copy `environments/dev.env.example` to `environments/dev.env`
only if `dev.env` doesn't already exist (never overwrite a live one — see Step 2). List every var
in it that needs a real value (`BASE_URL` plus whatever username/password/token/api-key vars each
role needs) in your final report — don't try to guess or fill them.

## Step 5 — sync and validate the empty project

```
npx apitest sync
npx apitest check
```
`check` should pass with zero scenarios. If `sync` fails (spec URL unreachable, invalid OpenAPI
doc), stop and report the failure — don't fabricate a scenario against a spec that never synced.

## Step 6 — write one minimal scenario

Follow the `add-scenario` prompt's conventions (also in `docs/scenario-format.md`):
1. Pick one safe, side-effect-free operationId — prefer a `GET` list/read or health-check
   operation over anything that mutates state. Find candidates via
   `npx apitest describe <operationId>` or by grepping `.spec-cache/spec.json` for
   `"operationId"`.
2. Write `scenarios/smoke.scenario.yaml`:
   ```yaml
   # yaml-language-server: $schema=../schemas/scenario.schema.json
   name: smoke
   tags: [smoke]
   auth: none          # or a real role name from apitest.config.ts if the chosen operation requires it
   steps:
     - name: <short description>
       operation: <operationId>
       assert:
         - status: 200
   ```
   Only add `auth: <role>` if the operation actually requires it.
3. `npx apitest check` again to confirm the new scenario's operationId/params validate.
4. Regenerate IntelliSense: `npx apitest schema`.

Do not run `npx apitest run` yourself unless real credentials are already confirmed in
`environments/dev.env` (or the chosen operation needs none) — otherwise it will fail on
missing/placeholder values, which is expected and not a bug to chase.

## Step 7 — report

Summarize: target directory and old spec → new spec; exactly what was deleted (by category); what
`apitest init` auto-configured vs. needs manual review; the env vars still needing real values;
the new `scenarios/smoke.scenario.yaml` and whether `apitest check` passed; and the explicit next
step for the human — fill in `environments/dev.env`, then `npx apitest run --tag smoke`.
